# Olist: продажи и повторные покупки в MySQL

Учебный SQL-проект для портфолио аналитика. Цель — исследовать товарооборот, средний чек, повторные покупки и качество данных бразильского маркетплейса. Без дашборда.

**Стек:** MySQL 8.0+, SQL (JOIN, CTE, оконные функции, рекурсивный календарь), Python только для подготовки импорта и проверки.

## Основные результаты

- 99 441 заказ, 96 096 уникальных покупателей во всей базе.
- 96 478 delivered-заказов; стоимость товаров 13 221 498,11 BRL; средний чек 137,04 BRL.
- Повторные покупатели: 2 801 / 93 358 = 3,00% среди покупателей delivered-заказов.
- 610 товаров без категории; сохранены при анализе.

Интерпретация, ограничения и следующие вопросы: [findings](docs/findings.md).

## Структура

- sql/00_schema.sql — структура таблиц, для справки; уже включается в генерируемый импорт.
- sql/01_quality_checks.sql — контроль импорта и качества.
- sql/02_analysis.sql — решения заданий 1–19 с комментариями; выводы задания 20 в docs/findings.md.
- scripts/build_import.py — сборка SQL-импорта из оригинальных CSV, без внешних библиотек.
- scripts/validate_mysql.py — запуск аналитических запросов на локальном MySQL и контроль ключевых результатов.
- results/ — эталонные результаты расчётов и описание проверки; JSON, не исходные CSV.
- docs/review.md — проверка исходных заданий и темы для объяснения на собеседовании.

## Если база уже импортирована

1. Открыть sql/01_quality_checks.sql в Workbench и выполнить.
2. Открыть sql/02_analysis.sql, выполнить USE olist_analytics, затем нужный запрос целиком (включая WITH).
3. Сравнить результаты с results/. Ограничение вывода строк интерфейсом не означает потерю данных в базе.

## Воспроизведение с нуля

Источник: [Brazilian E-Commerce Public Dataset by Olist](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce), автор Olist, лицензия исходных данных CC BY-NC-SA 4.0. Исходные данные не включены в репозиторий. Условия лицензии источника применяются и к производным данным; ссылки на источник и авторство сохранены.

Скачать архив с Kaggle, извлечь в папку data пять CSV: olist_customers_dataset.csv, olist_orders_dataset.csv, olist_order_items_dataset.csv, olist_products_dataset.csv, product_category_name_translation.csv. Контрольные суммы исходных файлов находятся в docs/source_sha256.json.

```bash
python3 scripts/build_import.py --data-dir data --output-dir generated
mysql -h 127.0.0.1 -P 3306 -u root -p < generated/olist_mysql.sql
```

На Mac клиент может находиться по пути /usr/local/mysql/bin/mysql. Пароль вводится по запросу, в коде не хранится. Импорт создаёт новую базу olist_analytics и рассчитан на однократный запуск. Если она уже существует, не импортируйте заново: используйте раздел выше. Не выполняйте DROP ради повторного импорта и не используйте --force. При ошибке остановитесь и выясните причину.

## Проверка на MySQL

```bash
python3 -m pip install mysql-connector-python
python3 scripts/validate_mysql.py --user root
```

Скрипт запрашивает пароль скрыто, выполняет только аналитические SELECT/USE и сохраняет mysql_validation.json. База не изменяется. Текущий статус проверки: расчёты проверены на SQLite с адаптацией синтаксиса; исполнение на настоящем MySQL ещё требует подтверждения.

Скрипт scripts/validate_reference.py сохраняет использованный способ проверки через sqlglot и SQLite (для него нужны sqlglot и локальная SQLite-копия тех же данных). Для обычной работы с проектом достаточно MySQL.

## Модель данных

customers.customer_id → orders.customer_id (одна клиентская запись на заказ в этой выборке); orders.order_id → order_items.order_id (один ко многим); products.product_id → order_items.product_id (один ко многим). category_translation соединяется по product_category_name через LEFT JOIN. Для анализа людей используется customers.customer_unique_id.
